## Part 1 — Engine research

The question: what hosts tainer's Linux guest (cyberstack-agent plus crun) on Windows, given the hard constraints that **Windows Home must work** and **8 GB RAM is the floor**, with Docker Desktop on an 8 GB machine ("works, hell slow") as the bar to beat. Everything below is research, not decision; the decision is made with Leni once the laptop exists.

**Part 2 claims, checked.** Part 2 was written before this sourcing. Four of its claims were flagged:

1. *NRPT rules cannot carry a port* (Part 2, `pkg/tainer/dns/resolver.go:16`, `internal/dns/responder.go:19`). **Confirmed.** `Add-DnsClientNrptRule -NameServers` takes a list of DNS server addresses, and its documentation gives no port syntax, while the same cmdlet's `-DAProxyServerName` explicitly documents `hostname:port` forms ([Add-DnsClientNrptRule](https://learn.microsoft.com/en-us/powershell/module/dnsclient/add-dnsclientnrptrule)). So the tainer.me responder has to answer on `127.0.0.1:53` (or another loopback address on :53). Whether :53 on loopback is free on a stock Home install (Internet Connection Sharing, the WSL DNS proxy) is **needs laptop**.
2. *AF_UNIX on Windows 10 1803+ "may work as is"* (Part 2, `internal/httpapi/server.go:114`). **Confirmed for host-local use, corrected for the guest boundary.** Windows AF_UNIX arrived in Insider build 17063 (released as 1803) with stream sockets only: no `SOCK_DGRAM`/`SOCK_SEQPACKET`, no ancillary data (so no `SCM_RIGHTS` fd passing), no autobind, and no `socketpair` in Winsock ([AF_UNIX comes to Windows](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/)). Go's `net` package supports it on Windows ([golang/go#26072](https://golang.org/issue/26072)), so a host-side `net.Listen("unix", …)` in cyberstackd can work. What does **not** work is crossing into WSL2: Windows/WSL AF_UNIX interop was built for WSL1 ([Windows/WSL interop with AF_UNIX](https://devblogs.microsoft.com/commandline/windowswsl-interop-with-af_unix/)) and the closest tracked WSL2 request is [microsoft/WSL#5961](https://github.com/microsoft/WSL/issues/5961), which covers socket files on `/mnt` (Windows) paths and has been open since 2020. An AF_UNIX socket cannot be the host↔guest hop.
3. *The hv_sock service-GUID template* (Part 2, `cmd/cyberstack-agent/main.go:42`). **Confirmed.** Microsoft documents the Linux-guest VSOCK template `00000000-facb-11e6-bd58-64006a7986d3` with the port number written into the first field, so vsock port 1024 maps to `00000400-FACB-11E6-BD58-64006A7986D3`. A host-side listener needs its service GUID registered under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Virtualization\GuestCommunicationServices` (admin), and the Linux guest needs `CONFIG_VSOCKET` and `CONFIG_HYPERV_VSOCKETS` ([Make your own integration services](https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/user-guide/make-integration-service)). go-winio implements the mapping as `VsockServiceID(port)` alongside `ListenHvsock` and `Dial` ([go-winio hvsock.go](https://github.com/microsoft/go-winio/blob/main/hvsock.go)). Whether the guest's `vsock.Dial(vsock.Host, …)` (host CID 2, `internal/transport/vsock_linux.go:15`) reaches the host unchanged over the hv_sock transport is **needs laptop**.
4. *gvproxy builds and ships on Windows* (Part 2, `cmd/cyberstackd/main.go:98`). **Confirmed, with a nuance.** gvisor-tap-vsock publishes `gvproxy-windows.exe` (amd64 and arm64) in its releases ([gvisor-tap-vsock releases](https://github.com/containers/gvisor-tap-vsock/releases)). Podman uses gvproxy on Windows for its Hyper-V provider and for WSL only when `--user-mode-networking` is set; default WSL machines use WSL's own networking ([podman-machine-init](https://docs.podman.io/en/latest/markdown/podman-machine-init.1.html)). Podman's Windows API endpoint is a different helper, win-sshproxy, which proxies Windows named pipes over SSH into the guest ([win-sshproxy main.go](https://github.com/containers/gvisor-tap-vsock/blob/main/cmd/win-sshproxy/main.go), launched from [podman machine_windows.go](https://github.com/containers/podman/blob/main/pkg/machine/machine_windows.go)).

### 1. Engine host options

**WSL2 with a tainer-owned distro.** WSL2 runs a real Linux kernel "inside a lightweight utility virtual machine" and runs distributions "as isolated containers inside the managed VM" ([Comparing WSL versions](https://learn.microsoft.com/en-us/windows/wsl/compare-versions)). Mechanically, `wslservice.exe` builds a JSON VM description and passes it to `HcsCreateComputeSystem()`; the VM boots the WSL kernel into `mini_init`, which mounts each distro's VHD and starts its init ([WSL boot process](https://wsl.dev/technical-documentation/boot-process/)). The code is open source except the WSL1 driver and the `\\wsl.localhost` redirector ([Open source WSL](https://learn.microsoft.com/en-us/windows/wsl/opensource)).

- *Edition*: WSL2 needs Windows 10 1903 (build 18362.1049+) on x64 or Windows 11, plus the **Virtual Machine Platform** optional feature and a reboot ([manual install](https://learn.microsoft.com/en-us/windows/wsl/install-manual)). No edition restriction is stated, and Rancher Desktop explicitly supports "Windows 11 (including Home edition)" on top of it ([Rancher Desktop install](https://docs.rancherdesktop.io/getting-started/installation/)). Windows 10 itself left support on 2025-10-14 ([Windows 10 lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro)), so Windows 11 is the realistic target.
- *Custom distro*: `wsl --import <Distro> <InstallLocation> <FileName>` takes a rootfs tar (or a VHDX with `--vhd`; `--import-in-place` registers an existing ext4 VHDX) and needs no Store package ([custom distro](https://learn.microsoft.com/en-us/windows/wsl/use-custom-distro), [basic commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)). That fits our boot-artifact pipeline: we ship a rootfs tar instead of an EFI raw disk.
- *Control surface from Go*: `wsl.exe` (`--import`, `--unregister`, `--terminate`, `--shutdown`, `-d <distro> -u root -- <cmd>`, `-l -v`) as a subprocess, or the Win32 `wslapi.h` functions (`WslRegisterDistribution`, `WslLaunch`, `WslConfigureDistribution`) ([wslapi.h](https://learn.microsoft.com/en-us/windows/win32/api/wslapi/)). Gotcha: `wsl.exe` writes UTF-16LE unless `WSL_UTF8=1` is set (added in WSL 0.64.0, [microsoft/WSL#4607](https://github.com/microsoft/WSL/issues/4607)).
- *Lifecycle realities*: there is **one** utility VM for all of the user's WSL2 distros. Its settings (`memory`, `processors`, `kernel`, `swap`, networking mode) live in the single per-user `%UserProfile%\.wslconfig`; a distro is stopped after `instanceIdleTimeout` (15 s) and the VM after `vmIdleTimeout` (60 s, Windows 11) ([WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)). Whether a distro that only runs our long-lived agent counts as "idle" (and so needs a held-open `wsl.exe` process, which is what the incumbents appear to do) is **needs laptop**. `wsl --shutdown` from any app kills every distro, ours included ([basic commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)). `isolateDistroCgroup` (default true) gives each distro its own cgroup, which is where smart-pod budgets would sit ([WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)).
- *Installer implications*: if WSL is absent, enabling it needs admin and a reboot; `wsl --install --no-distribution` installs only the platform ([basic commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)).

**WSL containers (`wslc.exe` and the WSL container API).** New in 2026 and worth tracking: WSL 2.9.3+ ships a container CLI and a NuGet API (`Microsoft.WSL.Containers`, C#/C++/C) whose `Session` object is "a WSL-backed host that runs your containers" ([WSL container](https://learn.microsoft.com/en-us/windows/wsl/wsl-container)). Sessions have their **own** CPU, memory, storage path and idle timeout, configured in code via `SessionSettings`, and `.wslconfig` does not apply to them; the settings page calls it "the session VM" ([WSL container settings](https://learn.microsoft.com/en-us/windows/wsl/wsl-container-settings)). It is a public preview targeting general availability in fall 2026, with virtiofs as the default file system ("2x faster" Windows file access) and the experimental `consomme` networking mode ([WSL container public preview](https://devblogs.microsoft.com/commandline/wsl-container-is-now-available-for-public-preview/)). It is its own container runtime with no documented Docker-compatible socket, so it would host our agent only if a session can run a privileged long-lived container (**needs laptop**), and Go would reach it through COM/WinRT or a small helper. Home support is not stated (**needs laptop**).

**Direct HCS (our own utility VM, the way WSL does it).** The Host Compute System API creates and controls VMs from a JSON document; the caller prepares the VHD, the network (HCN) and any Hyper-V sockets itself ([HCS overview](https://learn.microsoft.com/en-us/virtualization/api/hcs/overview)). WSL's own engine proves it can boot a Linux kernel with hv_sock and Plan 9 shares on any machine WSL2 runs on. Whether a **third-party** process may call HCS on Home with only Virtual Machine Platform enabled is not documented anywhere we found (**needs laptop**: call `HcsCreateComputeSystem` from a test binary). Go has precedent bindings in [microsoft/hcsshim](https://github.com/microsoft/hcsshim), though its utility-VM paths target Windows containers.

**Windows Hypervisor Platform (WHP) plus our own VMM.** WHP is a user-mode API for "third-party virtualization stacks" (QEMU's WHPX accelerator, VirtualBox): partitions, vCPU run loops, guest memory mapping, interrupt controller emulation, and nothing else ([Hyper-V APIs](https://learn.microsoft.com/en-us/virtualization/api/), [WHP API](https://learn.microsoft.com/en-us/virtualization/api/hypervisor-platform/hypervisor-platform)). Every device (virtio-blk, net, vsock, a file share) is ours to emulate. It is enabled as the `HypervisorPlatform` optional feature; QEMU tests it from Windows 10 2004 on x86_64 ([QEMU WHPX](https://www.qemu.org/docs/master/system/whpx.html)). Home availability is reported anecdotally but not in Microsoft's docs (**needs laptop**). Realistic effort: writing or embedding a VMM is a project the size of cyberstack itself; shipping QEMU instead buys devices but not a fast file share, and puts a large GPL binary in our installer.

**Full Hyper-V VMs.** Hyper-V "can't be installed on Windows 10 Home or Windows 11 Home"; it needs Pro/Enterprise, SLAT and at least 4 GB ([install Hyper-V](https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/quick-start/enable-hyper-v)). Podman's Hyper-V provider also requires membership in Hyper-V Administrators or a one-off `podman system hyperv-prep` ([Podman for Windows](https://github.com/containers/podman/blob/main/docs/tutorials/podman-for-windows.md)). Documented, then **deprioritized**: it fails the Home constraint.

*What this means for tainer:* WSL2 is the only option that is documented to work on Home today, and it already does the hard parts (kernel, hv_sock, Plan 9, port relay). Its cost is that the VM is shared and configured globally per user, so tainer cannot own the VM budget the way cyberstackd does with vfkit on macOS without touching the user's `.wslconfig`. The WSL container session and direct HCS are the two paths that would give tainer its own fixed-size VM on the same platform; both need a laptop experiment before they can be weighed. WHP and Hyper-V are out for a first milestone.

### 2. Incumbents

**Docker Desktop.** Runs in its own `docker-desktop` WSL distro; integration with the user's distros is opt-in ([Docker Desktop WSL 2 backend](https://docs.docker.com/desktop/features/wsl/)). The engine is exposed to Windows as the named pipe `npipe:////./pipe/docker_engine` (TCP `localhost:2375` is opt-in) ([Docker Desktop FAQ](https://docs.docker.com/desktop/troubleshoot-and-support/faqs/general/)). A SYSTEM service, `com.docker.service`, listens on `//./pipe/dockerBackendV2` for privileged operations, and networking runs in a user-space process that inherits the user's firewall, VPN and proxy settings ([Windows permission requirements](https://docs.docker.com/desktop/setup/install/windows-permission-requirements/)). Current requirements list Windows 10 22H2 / Windows 11 23H2 "Enterprise, Pro, or Education" and 8 GB RAM for both backends, while the same page says "Windows Home or Education editions only allow you to run Linux containers" ([Docker Desktop Windows install](https://docs.docker.com/desktop/setup/install/windows-install/)). The Home position is therefore ambiguous on paper; **needs laptop**.

**Podman machine.** Each machine is a WSL2 distro (a custom Fedora image) or a Hyper-V VM; the two providers cannot run at once, and Hyper-V needs Pro ([Podman for Windows](https://github.com/containers/podman/blob/main/docs/tutorials/podman-for-windows.md), [podman-machine-init](https://docs.podman.io/en/latest/markdown/podman-machine-init.1.html)). The API reaches Windows through win-sshproxy, which serves `npipe:////./pipe/docker_engine` (or a per-machine pipe if that name is taken) and tunnels to the guest's socket over SSH ([machine_windows.go](https://github.com/containers/podman/blob/main/pkg/machine/machine_windows.go)). On WSL, every drive is auto-mounted under `/mnt`, so `--volume` is redundant.

**Rancher Desktop.** Windows 11 including Home, WSL required beforehand, 8 GB and 4 CPUs recommended; ships as an MSI with per-user or per-machine scope, and only the per-machine install gets the privileged service that can expose ports beyond `127.0.0.1` ([Rancher Desktop install](https://docs.rancherdesktop.io/getting-started/installation/)). It uses two WSL distros, `rancher-desktop` and `rancher-desktop-data`. Its experimental gvisor-based network stack (from wsl-vpnkit) exists for VPN compatibility ([Rancher Desktop 1.8](https://suse.com/c/rancher_blog/rancher-desktop-1-8-now-with-additional-configuration-options-and-more), [wsl-vpnkit](https://github.com/sakai135/wsl-vpnkit)). Lima, the Colima base, has an experimental `wsl2` driver that imports a rootfs tar and drives it over the built-in OpenSSH client ([Lima WSL2](https://lima-vm.io/docs/config/vmtype/wsl2/)).

**What users complain about (all three inherit it from WSL2):**

- *vmmem ballooning*: "WSL 2 consumes massive amounts of RAM and doesn't return it", open since 2019 ([microsoft/WSL#4166](https://github.com/microsoft/WSL/issues/4166)); 100% memory on a 16 GB laptop with Docker ([microsoft/WSL#8725](https://github.com/microsoft/WSL/issues/8725)); Docker backend growth needing restarts every few days ([docker/for-win#13668](https://github.com/docker/for-win/issues/13668)).
- *9P file I/O*: "[wsl2] filesystem performance is much slower than wsl1 in /mnt", open since 2019; a 2026 comment still measures `find` on `/mnt/c` at about 12 s against about 1 s on WSL1 ([microsoft/WSL#4197](https://github.com/microsoft/WSL/issues/4197)).
- *Clock drift after sleep*: WSL added host-time sync on resume in build 18970 ([WSL release notes](https://learn.microsoft.com/en-us/windows/wsl/release-notes)), but reports of minutes-to-hours drift continued ([microsoft/WSL#8204](https://github.com/microsoft/WSL/issues/8204), [microsoft/WSL#10006](https://github.com/microsoft/WSL/issues/10006)), breaking TLS and apt ([microsoft/WSL#4149](https://github.com/microsoft/WSL/issues/4149)).
- *Firewall prompts*: users cannot tell what `com.docker.backend.exe` is asking for, and the dialog names no port ([Docker forum thread](https://forums.docker.com/t/can-someone-tell-me-what-docker-is-trying-to-do-through-windows-firewall/98108)).

*What this means for tainer:* all three incumbents chose WSL2 and a named pipe for the API, which validates the platform and the transport. Their common pain (memory that never comes back, slow cross-OS mounts, drift after sleep, unexplained firewall dialogs) is WSL2's, not theirs, so tainer only beats them by making different choices on exactly those four points: a hard memory cap, a deliberate file strategy, a time resync on resume, and pre-staged firewall rules.

### 3. Socket transport host↔guest

Two hops matter: **CLI → daemon** on the Windows host (today `DOCKER_HOST=unix://…`, Part 2 `pkg/tainer/runtime/runtime.go:129`/`:138`, `pkg/tainer/engine/client.go:31`/`:53`) and **daemon → agent** across the VM boundary (today vfkit's vsock proxy, Part 2 `internal/daemon/daemon.go:119`, `internal/transport/vsock_linux.go:15`).

| Transport | Carries the Docker-API socket? | Crosses into the WSL2 VM? | Seams it satisfies (Part 2) |
|---|---|---|---|
| Named pipe (`\\.\pipe\…`) | Yes. The Docker SDK understands `npipe://`, and Docker Desktop and Podman both serve `docker_engine` this way ([Docker FAQ](https://docs.docker.com/desktop/troubleshoot-and-support/faqs/general/), [machine_windows.go](https://github.com/containers/podman/blob/main/pkg/machine/machine_windows.go)). Access control is a pipe security descriptor (go-winio `ListenPipe`). | No (host only) | CLI→daemon: `runtime.go:129/135/138` (URL instead of path, dial-and-ping instead of `os.Stat`), `client.go:53`, `internal/httpapi/server.go:114/118` |
| AF_UNIX on Windows | Yes on the host (Go supports it, [golang/go#26072](https://golang.org/issue/26072)); stream only, no fd passing ([AF_UNIX blog](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/)) | No ([microsoft/WSL#5961](https://github.com/microsoft/WSL/issues/5961)) | Would leave `server.go:114` unchanged, but third-party Docker clients on Windows expect `npipe://` |
| AF_HYPERV / AF_VSOCK (hv_sock) | Yes, as the daemon↔agent hop | Yes; needs the VM ID plus the service GUID, and registry registration for host listeners ([integration services](https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/user-guide/make-integration-service)) | daemon→agent: `daemon.go:119` becomes a transport interface; guest side `vsock_linux.go:15` and the port-1024 default (`cmd/cyberstack-agent/main.go:42`) stay as they are if the CID works (**needs laptop**) |
| Loopback TCP via `localhostForwarding` | Technically yes | Yes (WSL relays VM ports to Windows `localhost`, [WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)) | Simplest, but any local process can connect without a check; Docker keeps TCP opt-in for that reason |
| `wsl.exe` stdio relay | Yes (one connection per process) | Yes | Fallback only; one subprocess per connection |

WSL itself runs stdin/stdout/stderr and its control channels over hvsockets ([WSL technical docs](https://wsl.dev/technical-documentation/), [boot process](https://wsl.dev/technical-documentation/boot-process/)). The open question for a WSL2 distro is how a third-party host process learns the utility VM's ID: `Get-VM` does not list it, and the only pointer we found is `hcsdiag list`, from a third-party package page ([Ookii.VmSockets](https://www.nuget.org/packages/Ookii.VmSockets/1.0.0-preview)) — **needs laptop**. If the agent *listens* in the guest and the host *dials*, no registry entry is needed; if the agent dials the host (our current direction, `cmd/cyberstack-agent/main.go:126`), the installer must register the service GUID.

*What this means for tainer:* use a **named pipe** for CLI→daemon on Windows (Docker-native, ACL-able, and it drops straight into the `DOCKER_HOST` scheme seam), and **hv_sock** for daemon→agent, keeping the guest's AF_VSOCK code. The first laptop experiment is "dial the agent in our WSL distro from a Go host process over hv_sock". If that fails, loopback TCP behind a token (or the `wsl.exe` relay) is the fallback.

### 4. File sharing

tainer bind-mounts the project directory into containers (Part 2 `pkg/tainer/pod/start.go:575`), and on macOS that share (Apple virtio-fs via vfkit) was the performance battleground: `git status` on a ~19.6k-file WordPress repo took ~0.6 s warm and several seconds cold, and the agreed direction is guest-side cache tuning, never a sync layer like Mutagen (filesystem-roadmap memory, 2026-07-12).

- **9P (DrvFs, `/mnt/c`)** is WSL2's default for Windows drives: `wslservice.exe` runs a Plan 9 server per session and `mount.drvfs` mounts it as plan9, virtio-plan9 or virtiofs depending on `.wslconfig` ([DrvFs internals](https://wsl.dev/technical-documentation/drvfs/)). This is the slow path users complain about ([microsoft/WSL#4197](https://github.com/microsoft/WSL/issues/4197)). The reverse direction (Windows tools reading `\\wsl.localhost\…`) goes through the closed-source P9rdr redirector ([Open source WSL](https://learn.microsoft.com/en-us/windows/wsl/opensource)).
- **"Keep the code in ext4"** is Microsoft's and Docker's own advice: performance across OS file systems is the one area WSL2 loses to WSL1 and is "addressed by storing your project files on the same operating system as the tools" ([Comparing WSL versions](https://learn.microsoft.com/en-us/windows/wsl/compare-versions)); Docker says bind mounts are "much higher" performance from the Linux filesystem, and inotify events only arrive for files there ([Docker WSL best practices](https://docs.docker.com/desktop/features/wsl/best-practices/)). That matters for our dev servers' live reload.
- **virtiofs** exists as an experimental `.wslconfig` switch (`virtiofs=true`) ([WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)) and is the default for WSL container sessions, claimed "2x faster" ([WSL container preview](https://devblogs.microsoft.com/commandline/wsl-container-is-now-available-for-public-preview/)). A 2026 commenter on #4197 saw "no significant improvement" with it. Unmeasured for our workload (**needs laptop**).
- **Dev Drive** (ReFS plus Defender performance mode, Windows 11 22621.2338+, all SKUs, 50 GB minimum) explicitly gives **no** gain for WSL: "you should not expect to see any performance improvement when accessing project files in Dev Drive from a Linux distribution running via WSL", and the DrvFs `metadata` option does not work on ReFS ([Dev Drive](https://learn.microsoft.com/en-us/windows/dev-drive/)). It only helps Windows-native tools.

Proposed measurement bands for the laptop, on the same ~19.6k-file WordPress repo used on macOS: **pass** if warm `git status` in the pod is ≤ 1.0 s and a host-side edit reaches the container's inotify watcher in ≤ 1 s; **fail** if warm `git status` is > 3 s or edits are not seen without polling. Run each over `/mnt/c` (9P), `/mnt/c` with `virtiofs=true`, and the distro's own ext4.

*What this means for tainer:* the macOS model (project lives on the host, shared into the VM) is the slow path on Windows by every source we found. The likely answer is to flip it: project directories live in the tainer distro's ext4 and Windows editors reach them over `\\wsl.localhost\tainer\…` (or VS Code Remote-WSL), with `/mnt/c` kept as a supported but slower mode. That is a product decision for Leni (it changes where `tainer init` puts files) and it needs the bands above measured first. Part 2's path-translation seam (`start.go:575`) is needed either way.

### 5. Ports and firewall

- **Router on :80/:443/:22.** In WSL's default NAT mode, `localhostForwarding` (default true) makes ports bound to wildcard or localhost in the VM reachable from Windows at `localhost:port` ([WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)), relayed by WSL's `localhost` daemon ([WSL technical docs](https://wsl.dev/technical-documentation/)). Reaching the VM from the LAN in NAT mode needs `netsh interface portproxy` ([WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking)). The alternative is our own host-side forwarder (Part 2 notes `internal/vm/hybridforwarder`), which would bind `127.0.0.1` in cyberstackd.
- **Mirrored mode** (`networkingMode=mirrored`) gives IPv6, `127.0.0.1` both ways, better VPN compatibility and LAN access, but requires **Windows 11 22H2+**; `dnsTunneling` (default on there) answers DNS through a virtualization channel for VPN compatibility ([WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking)). Neither page restricts it by edition; Home behavior is **needs laptop**. This is the Windows counterpart of our NordVPN finding (gvproxy out-of-process on macOS).
- **Windows Defender Firewall.** The first time an app listens without an allow rule, an admin user is prompted and a "No" or cancel creates block rules; a **non-admin** user gets block rules whatever they click ([firewall rules](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules)). Microsoft's own recommendation is to stage allow rules at install time, which an MSI can do. Separately, since Windows 11 22H2 the **Hyper-V firewall** filters WSL traffic (WSL VMCreatorId `{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}`), with loopback between host and WSL allowed by default ([Hyper-V firewall](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/hyper-v-firewall)). Whether a loopback-only listener triggers the prompt at all is **needs laptop**.
- **DNS (tainer.me).** NRPT rule for `.tainer.me` pointing at a loopback responder on :53, as confirmed above.

*What this means for tainer:* bind everything to loopback, let WSL's relay or our own forwarder carry :80/:443/:22 to Windows `localhost`, and have the installer pre-create firewall rules so a user never sees an unexplained dialog. Part 2's port pre-check (`pkg/tainer/router/ensure.go:43`) and the sshd service probe (`:146`/`:149`) remain needed, because IIS/http.sys or the OpenSSH Server service can hold those ports.

### 6. Memory discipline

- **WSL2 defaults on an 8 GB machine**: `memory` defaults to 50% of host RAM (4 GB) and `swap` to 25% (2 GB), set only in the global `.wslconfig` ([WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)).
- **Reclaim**: WSL2 historically did not return page cache to Windows until shutdown ([Comparing WSL versions](https://learn.microsoft.com/en-us/windows/wsl/compare-versions), [microsoft/WSL#4166](https://github.com/microsoft/WSL/issues/4166)). `autoMemoryReclaim` (`gradual` / `dropCache` / `disabled`) now sits under `[experimental]` with `dropCache` documented as the default ([WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)); Docker still describes it as something to "consider enabling" ([Docker WSL backend](https://docs.docker.com/desktop/features/wsl/)). Which WSL version flipped the default is not stated, so the laptop must check `wsl --version` and observe reclaim (**needs laptop**).
- **Owning the budget**: tainer cannot set the WSL VM's size without editing the user's `.wslconfig`, which also changes their Ubuntu and anything else. Within the VM we do control cgroups (`isolateDistroCgroup`, [WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)), so smart pods (nano 512M … xxl 16G on `tainer-<project>`) still cap our containers; they just cannot shrink the VM. A WSL container session (`memorySize`, own idle timeout, [WSL container settings](https://learn.microsoft.com/en-us/windows/wsl/wsl-container-settings)) or a direct-HCS VM would restore the macOS model of a fixed VM we size ourselves.
- **What fits in 8 GB**: Windows 11 idle, a browser and an editor have to share the box with the VM. We have no primary-source numbers for those on the target machine; the laptop should record idle commit charge with nothing running, then with Edge plus VS Code, then with one nano pod (**needs laptop**). Docker and Rancher both list 8 GB as a requirement or recommendation, which suggests they treat it as their floor too ([Docker install](https://docs.docker.com/desktop/setup/install/windows-install/), [Rancher install](https://docs.rancherdesktop.io/getting-started/installation/)).

*What this means for tainer:* on WSL2 the honest pitch is "tainer's containers never exceed their pod budget, and tainer's distro idles to near zero"; the VM ceiling itself stays WSL's. If the laptop shows the shared VM ballooning anyway, that is the trigger to move to an owned session or HCS VM, not to start editing `.wslconfig` behind the user's back.

### 7. Packaging and trust

- **Formats.** MSIX gives clean install and uninstall, differential updates and App Installer auto-update ([MSIX overview](https://learn.microsoft.com/en-us/windows/msix/overview)), but it cannot write HKLM (writes are virtualized), cannot install drivers, does not support per-user services, and should not need elevation ([prepare to package](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-prepare)). Our installer needs HKLM (the hv_sock service GUID), firewall rules, an NRPT rule and possibly enabling Virtual Machine Platform, so **MSI** (as Rancher Desktop ships) fits better. **winget** accepts MSI, MSIX and EXE installers through a manifest PR to `microsoft/winget-pkgs`, as long as the installer runs silently ([winget manifest](https://learn.microsoft.com/en-us/windows/package-manager/package/manifest)).
- **Signing cost and SmartScreen.** Azure Artifact Signing (formerly Trusted Signing) is about $9.99/month and open to organizations in the USA, Canada, the EU and the **UK** (Cyber5 IO qualifies), with no hardware token and CI integration; OV certificates run $150–300/year and must live on an HSM; EV is $400+/year and **since 2024 no longer bypasses SmartScreen** ([code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)). Artifact Signing issues no EV certificates and needs a paid Azure subscription ([Artifact Signing FAQ](https://learn.microsoft.com/en-us/azure/trusted-signing/faq)).
- **Reputation mechanics.** SmartScreen weighs publisher reputation and file-hash reputation; new signed files warn until they gather history, which "can take several weeks and hundreds of clean installs", and reputation carries across versions only with the same signing identity. On Windows 11, Smart App Control can block unsigned executables outright ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). Only Store-distributed MSIX skips the warning entirely.
- **Auto-update analog.** Our macOS `.pkg` postinstall stops the old engine and the boot disk refreshes from a provenance sidecar (upgrade-handover memory). The Windows equivalent is an MSI major upgrade with a custom action that asks cyberstackd to shut down (through the Part 2 control-pipe seam, since there is no SIGTERM) before files are replaced, plus `winget upgrade` as the delivery channel.

*What this means for tainer:* MSI, signed through Artifact Signing under Cyber5 IO, listed on winget. Budget for several weeks of SmartScreen warnings after launch regardless of certificate type, and keep one signing identity forever.

- **identity**: `pkg/tainer/identity/identity_unix.go` (reads uid/gid from file stat via `syscall.Stat_t`, line 17) and `pkg/tainer/identity/identity_windows.go` (returns 1000:1000). Complete.
- **process control**: `pkg/tainer/runtime/proc_unix.go` (`ProcessAlive`, `SignalTerm`, `SignalKill`, `detachAttr` with `Setsid`, `canSpawnDaemon`) and `pkg/tainer/runtime/proc_windows.go` (stubs returning `ErrUnsupportedOS`; `ProcessAlive` returns false). Added by Task 1 of this ticket.
- **terminal resize**: `cmd/tainer/resize_unix.go` (`SIGWINCH` watcher, line 14) and `cmd/tainer/resize_windows.go` (no-op). Added by Task 1.
- **compile gate**: `make cross` builds darwin/arm64, linux/amd64, linux/arm64 and windows/amd64 (Makefile:55-58).

### Exec/TTY note

Interactive `tainer exec`/attach reads the terminal size once before attach (cmd/tainer/main.go:1967) and, on unix, subscribes to `SIGWINCH` to resend it on every resize (cmd/tainer/resize_unix.go:14). Windows has no `SIGWINCH`, so `watchResize` is a deliberate no-op (cmd/tainer/resize_windows.go:7): the container pty keeps the initial size for the whole session and a resized terminal wraps incorrectly until the user re-attaches. Raw mode still works through `golang.org/x/term` (cmd/tainer/main.go:2287).

This is acceptable degradation for the first Windows milestone. The proper fix is a small poll of `term.GetSize` (about 250 ms) inside `resize_windows.go`, or console-buffer-size events from `ReadConsoleInput`, calling the same callback. It needs no change to shared code because the seam already exists.
