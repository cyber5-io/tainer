# Tainer 0.9 — Pod Lifecycle, Router Redesign, Network UX

**Date:** 2026-05-04
**Branch:** `dev/v1`
**Step:** 8 of the master rebuild plan (`docs/superpowers/specs/2026-04-23-tainer-rebuild-cyberstack-design.md`)
**Predecessors:** Step 5 (legacy/ move + fresh module), Step 6 (port survivors), Step 7 (transparent cyberstackd bring-up). All three landed on `dev/v1`. Step 6 stashed `pkg/tainer/router/lifecycle.go`, `pkg/tainer/project/*`, and `pkg/tainer/tui/mount/` back to `legacy/` because they encoded the podman pod model — this spec defines what replaces them.
**Successor:** Step 9 (parity validation), Step 10 (DDEV integration), Step 11 (installer signing).

## Goal

Replace the legacy podman-pod orchestration with a topology cyberstackd can run, while keeping tainer's pod abstraction as a first-class architectural concept. Ship the 10 lifecycle commands needed for the MVP. Deliver `tainer network mode set performance|compatibility` so users can flip between vmnet-helper and external-gvproxy when their host networking changes (notably under VPN).

## Version retargeting

The original master rebuild spec targeted **1.0.0**. This spec retargets that milestone to **0.9.0**, reserving 1.0.0 for the smart-pod cap stone (aggregate cgroup enforcement). The motivation:

- 0.9 ships static pods (per-container resource limits, declared via pod-size presets).
- 1.0 ships smart pods (aggregate-pod cgroup enforcement) — the architectural promise that makes commercial Blenzi hosting viable.
- Calling this milestone "1.0" would over-promise the resource story.

Doc updates that follow this rename:
- `Makefile`: `VERSION := 0.9.0-dev`
- `README.md`: rebuild towards 0.9 not 1.0
- `CLAUDE.md`: current target 0.9.0
- `docs/superpowers/specs/2026-04-23-tainer-rebuild-cyberstack-design.md`: status note + step renumbering. Step 12 ("Ship 1.0.0") becomes "Ship 0.9.0"; a new roadmap entry for 1.0.0 follows it.

## Strategic decisions (locked in)

| Decision | Choice | Why |
|---|---|---|
| Topology | Per-pod /24 bridge; router multi-attaches to every pod network | Matches 0.2.x mental model; preserves project isolation; cyberstack's NetworkConnect supports it |
| Pod abstraction | First-class architectural concept (a pod = network + N labeled containers + resource budget) | Same lifecycle unit as 0.2.x; reserves the slot for smart-pod aggregate enforcement in 1.0 |
| Resource model | Per-container limits via Docker `HostConfig.Resources`, computed from manifest pod-size preset | Cyberstack 0.4 supports this today; aggregate enforcement waits for cyberstack 0.5 |
| DNS | Embedded responder in cyberstackd on `127.0.0.1:7753`, `/etc/resolver/tainer.me` at install time | No dnsmasq image, fully offline-capable, port matches 0.2.x for continuity |
| Container addressing | By IP, regenerate caddy/sshpiper config + reload on every lifecycle event | Mirrors 0.2.x; cyberstackd's container-DNS-by-name is post-1.0 work |
| Discovery | Engine labels (`tainer.pod`, `tainer.role`, etc.); single source of truth | No drift between local registry and engine state |
| Network mode UX | `tainer network mode set perf\|compat` — auto-stops running pods, restarts daemon, restarts pods | One command for the VPN-flip scenario |
| SSH bind | sshpiper binds host `:2222`; `pf` redirect `:22 → :2222` always enabled | Users expect `ssh project@ssh.tainer.me` (no port) per 0.2.x UX |
| Sudo | All sudo at install time only; runtime never asks | One macOS `.pkg` postinstall script handles every privileged operation |
| Auto-port-publish | Range 30000-39999, allocation cached in container labels | Above common dev defaults, below macOS ephemeral range, persistent across restarts |
| `.tainer.local.yaml` overlay | Deep-merge over `tainer.yaml`; gitignored by default | Same pattern as DDEV's `config.local.yaml` |

### Pod data model

#### Manifest schema (v2)

```yaml
version: 2
project:
  name: mywp
  type: wordpress              # wordpress | php | nodejs | nextjs | nuxtjs | nestjs | react | kompozi
  domain: mywp.tainer.me
  auto-open: true
runtime:
  php: "8.3"
  database: mariadb
  php-limits:                  # renamed from "limits" — clearer it's PHP-only
    memory_limit: 512M
    upload_max_filesize: 2G
    post_max_size: 2G
    max_execution_time: 300
    max_input_vars: 10000
pod:
  size: small                  # nano | small | medium | large | xlarge | xxl | custom
  # When size: custom:
  # containers:
  #   caddy: { memory: 128M, cpu: 0.25 }
  #   fpm:   { memory: 640M, cpu: 0.5 }
  #   db:    { memory: 256M, cpu: 0.25 }
mounts:
  - mounts-dir-name
ports:                          # v2 addition: dev-facing services to auto-publish on host
  - role: db
    container: 3306
  - role: mailpit
    container: 8025
```

#### Label scheme

| Label | Applied to | Value |
|---|---|---|
| `tainer.pod` | network + every container | pod (project) name |
| `tainer.role` | container only | role inside the pod (`caddy`, `fpm`, `node`, `db`, `mailpit`, etc.) |
| `tainer.manifest-path` | container only | absolute path to the manifest that was used at start |
| `tainer.manifest-hash` | container only | SHA of the resolved manifest (drift detection) |
| `tainer.published.<role>` | container only | if a port was auto-published for this role, the host port assigned |

Discovery query: `engine.ContainerList(Filters: tainer.pod=*)`, group by label. List networks similarly.

#### Naming convention

- Pod network: `tainer-<pod>` (e.g., `tainer-mywp`)
- Pod container: `tainer-<pod>-<role>` (e.g., `tainer-mywp-caddy`, `tainer-mywp-fpm`, `tainer-mywp-db`)
- Router containers (always-running): `tainer-router-caddy`, `tainer-router-ssh`

#### Pod-size → per-container split

Tainer computes the split at start time based on (project type, pod size). The user only declares pod size in the manifest; the table is implementation-internal and tunable until 1.0 freezes it.

For PHP-based projects (`wordpress`, `php`, `kompozi`) — 3 containers (caddy + fpm + db):

| size | total | caddy | fpm | db |
|---|---|---|---|---|
| nano | 512M / 0.5 | 64M / 0.1 | 320M / 0.25 | 128M / 0.15 |
| small | 1G / 1.0 | 128M / 0.25 | 640M / 0.5 | 256M / 0.25 |
| medium | 2G / 2.0 | 256M / 0.5 | 1280M / 1.0 | 512M / 0.5 |
| large | 4G / 4.0 | 512M / 1.0 | 2560M / 2.0 | 1G / 1.0 |
| xlarge | 8G / 4.0 | 1G / 1.0 | 5G / 2.0 | 2G / 1.0 |
| xxl | 16G / 8.0 | 2G / 1.0 | 10G / 6.0 | 4G / 1.0 |

For Node-based projects (`nodejs`, `nextjs`, `nuxtjs`, `nestjs`, `react`, `kompozi`) — 3 containers (caddy + node + db; the role for the second container is `web` for React, `node` for the rest, but the split is identical):

| size | total | caddy | node/web | db |
|---|---|---|---|---|
| nano | 512M / 0.5 | 64M / 0.1 | 320M / 0.25 | 128M / 0.15 |
| small | 1G / 1.0 | 128M / 0.25 | 640M / 0.5 | 256M / 0.25 |
| medium | 2G / 2.0 | 256M / 0.5 | 1280M / 1.0 | 512M / 0.5 |
| large | 4G / 4.0 | 512M / 1.0 | 2560M / 2.0 | 1G / 1.0 |
| xlarge | 8G / 4.0 | 1G / 1.0 | 5G / 2.0 | 2G / 1.0 |
| xxl | 16G / 8.0 | 2G / 1.0 | 10G / 6.0 | 4G / 1.0 |

CPU tapers at the high end so we don't overcommit on typical Apple Silicon dev machines (8-10 cores). The split also caps at `host_cpu_count - 1`; tainer prints a one-line warning if the requested split exceeds available cores.

#### Role mapping per project type

The label `tainer.role` is the single source of truth for "which container does what" inside a pod. Values per type:

| Project type | Roles |
|---|---|
| `wordpress`, `php`, `kompozi` (PHP-based) | `caddy`, `fpm`, `db` |
| `nodejs`, `nextjs`, `nuxtjs`, `nestjs` | `caddy`, `node`, `db` |
| `react` | `caddy`, `web`, `db` |

`tainer exec <project>` defaults to the role that runs the user's app (`fpm` for PHP, `node`/`web` for the rest). `tainer exec <project> caddy -- ...` targets the project's edge caddy explicitly.

The escape hatch for users who want stable absolute numbers: `pod.size: custom` with explicit per-container overrides. Tainer leaves those alone forever.

### Engine state-of-the-world

cyberstack 0.4 supports everything the lifecycle needs:
- Networks: `NetworkCreate` with subnet, `NetworkConnect`/`Disconnect`, `NetworkRemove`, `NetworkList`
- Containers: `ContainerCreate` with `HostConfig.Resources` (Memory, NanoCPUs), `Start`, `Stop`, `Remove`, `Inspect`, `List` (with label filter)
- Exec: `ContainerExecCreate` + `ContainerExecAttach` + stdcopy demux
- Logs: `ContainerLogs`
- Volumes: `VolumeCreate` (used for persistent DB)
- Pull: `ImagePull`

The only missing piece tainer needs is **container-DNS-by-name on user-defined bridges** (Docker's embedded resolver at 127.0.0.11). 0.9 works around this by addressing-by-IP. Adding it to cyberstack is a 1.0+ improvement; the addressing layer in `pkg/tainer/router` is a single function so swapping later is a small diff.

## Runtime behaviors

### Project lifecycle

#### `tainer start [project]`

1. Discover the manifest (cwd or argument) and overlay `.tainer.local.yaml` if present → resolved manifest
2. Resolve pod-size split for project type → per-container `HostConfig.Resources`
3. `engine.NetworkCreate("tainer-<pod>", subnet)` (idempotent; subnet from `network.Allocator`, same /24 logic as 0.2.x)
4. Pull required images for the project type (registry image set per `project.type`; e.g., wordpress → `ghcr.io/cyber5-io/tainer-wordpress:<runtime.php>`)
5. For each container in the project type:
   - `engine.Run(spec)` with labels (`tainer.pod`, `tainer.role`, `tainer.manifest-hash`), resources, mounts (app, data, custom mounts), env (uid/gid, php-limits, project env, `TAINER_DOMAIN`), restart=`unless-stopped`
   - If a `ports:` entry targets this role, allocate a host port from 30000-39999 (probe-then-bind), record it as label `tainer.published.<role>=<port>`
6. `router.AttachToPod(eng, podName)` — `engine.NetworkConnect("tainer-<pod>", "tainer-router-caddy")` and same for `tainer-router-ssh`
7. Discover container IPs via `engine.Inspect`, render Caddyfile + sshpiper upstream files
8. Reload caddy via admin API `127.0.0.1:2019/load` (no container restart). sshpiper's `workingdir` plugin re-reads on next connection (no reload needed).
9. Run post-deploy script (`/opt/tainer/post-deploy.sh` inside the main container, idempotent)
10. Print summary:
    ```
    mywp started
      https://mywp.tainer.me
      ssh mywp@ssh.tainer.me
      mariadb on 127.0.0.1:30001 (db)
      mailpit on 127.0.0.1:30002 (mailpit)
    ```

#### `tainer stop [project]`

1. List `tainer.pod=<name>` containers via labels
2. `engine.Stop` each (graceful, default 10s timeout)
3. `router.UpdateConfig(eng)` — regenerate Caddyfile excluding this pod, reload caddy, remove sshpiper upstream entry
4. Router stays attached to the pod network. Cheap; avoids attach/detach churn on subsequent start.

#### `tainer destroy [project]` (with optional `--with-data`)

1. Stop (above)
2. `engine.Remove(force=true)` each container
3. `router.DetachFromPod(eng, podName)`
4. `engine.NetworkRemove("tainer-<pod>")`
5. Project source dir is **not** touched. The `--with-data` flag (post-0.9 idea) would delete `<project>/data/` after confirming with the user.

#### `tainer exec <project> [<role>] -- <cmd...>`

1. Default role: the type-specific app role (`fpm` for PHP-based, `node` for Node-based, `web` for React) — see the role mapping table above
2. `engine.Exec(ctx, "tainer-<pod>-<role>", cmd)`; stream output to user's tty
3. Interactive mode (`-it`) wires hijacked stdin/stdout/stderr; non-interactive captures and prints the final exit code

#### `tainer status [project]`

1. List `tainer.pod=<name>` containers via labels (or all pods if no project arg)
2. For each: print pod name, state (Running/Stopped/Mixed), domain, ssh, published ports
3. Probe `https://<domain>` for liveness; print "ready" or "not responding"

#### `tainer list` (alias `ls`)

1. Group all `tainer.pod=*` containers by pod name
2. Print a table: pod / type / state / domain / ports

#### `tainer db export <project>` and `tainer db import <project> <file>`

1. Lookup db container via labels: `tainer.pod=<name>`, `tainer.role=db`
2. Read project type to pick the dump command (mariadb-dump for WP/PHP/Kompozi; pg_dump for projects that pick postgres)
3. Run via `engine.Exec`, stream the output to a host file (export) or pipe in stdin (import)

### Router redesign

Two long-lived containers, no pod abstraction:

- `tainer-router-caddy`: image `caddy:2-alpine`, binds host `0.0.0.0:80,443`, mounts Caddyfile + cert/key, exposes admin API on `127.0.0.1:2019` (loopback inside the VM, port-forwarded to host for tainer's reload calls)
- `tainer-router-ssh`: image `farmer1992/sshpiperd:latest`, binds host `0.0.0.0:2222` (the `pf` anchor redirects `:22 → :2222`), mounts sshpiper workingdir + host key, runs `/sshpiperd/plugins/workingdir --root /var/sshpiper --no-check-perm --allow-baduser-name`

Lifecycle:
- `router.Ensure(eng)` — called by `tainer start` if either container is absent. Pulls images if needed, creates with the right binds, starts.
- `router.AttachToPod(eng, podName)` — `engine.NetworkConnect("tainer-<pod>", "tainer-router-caddy")` and same for sshpiper.
- `router.DetachFromPod(eng, podName)` — mirror in destroy.
- `router.UpdateConfig(eng)` — runs after every lifecycle event:
  - List all networks with `tainer.pod=*` label
  - For each, inspect the project's caddy container IP on that network
  - Regenerate Caddyfile (per-project site blocks: `<domain> { reverse_proxy <ip>:80 }`)
  - POST to caddy admin API at `127.0.0.1:2019/load` to apply (no container restart)
  - Regenerate sshpiper upstream files in the workingdir bind mount; sshpiper's `workingdir` plugin reads them on every new connection (no reload needed)

### Embedded DNS responder (cyber-stack work)

In the cyber-stack repo, new package `internal/dns/responder.go` (~50 lines, `github.com/miekg/dns`):

- Listens on UDP `127.0.0.1:<port>` (cyberstackd flag `-dns-port`, default `7753`)
- Returns `127.0.0.1` for any `*.tainer.me` A query
- Returns NXDOMAIN otherwise
- Started inside cyberstackd's `main`, lifecycle-bound to the daemon's context; clean shutdown on SIGTERM

Tainer side (`pkg/tainer/dns/resolver.go`, already exists for legacy work) is updated to:
- `Install(port int) error` — writes `/etc/resolver/tainer.me` with `nameserver 127.0.0.1\nport <port>`. Called by the `.pkg` postinstall script.
- `Verify(port int) (bool, error)` — reads back the file, checks correctness.
- `Remove() error` — deletes the file. Called by `tainer self-uninstall`.

`pkg/tainer/runtime/runtime.go` (Step 7) gains a `-dns-port=7753` flag passed when spawning cyberstackd.

### Network mode UX

```
tainer network mode                        # show current mode + active vfkit interface
tainer network mode show                   # alias
tainer network mode set perf|compat        # change (auto-restarts running pods)
```

Persistence: `~/.cyberstack/network-mode` (single file: `vmnet-helper` or `external-gvproxy`).

`runtime.Engine()` reads the file when spawning cyberstackd; passes `-network-mode=<value>`. Default if missing: `vmnet-helper`.

Switch flow (`tainer network mode set compat`):

1. Read current mode from file. If same → no-op, print status.
2. List all `tainer.pod=*` containers in `Running` state, group by pod → snapshot.
3. For each running pod: `tainer stop <pod>` (graceful).
4. Stop cyberstackd (SIGTERM → 30s grace → SIGKILL fallback). Existing 0.4 shutdown handler does the heavy lifting.
5. Write new mode to `~/.cyberstack/network-mode`.
6. `runtime.Engine(AutoStart=true)` — spawns cyberstackd in the new mode.
7. For each pod in the snapshot: `tainer start <pod>`. Continue past individual failures.
8. Print summary:
   ```
   Switched to compatibility mode (external-gvproxy).
     Restarted: mywp, mynext
     Failed:    (none)
   ```

Failure handling:
- Step 4 (cyberstackd hangs): SIGKILL after grace window, log.
- Step 6 (new mode broken on this host): revert mode file, retry start in old mode, surface clear error: `compatibility mode failed to start; reverted to performance. Reason: <stderr>`.
- Step 7 (some pod fails to start in new mode): keep going, summarize at end. User can investigate per-pod via `tainer status <pod>`.

### SSH placement

sshpiper binds host `0.0.0.0:2222`. The `pf` anchor `tainer` (installed by the postinstall script) carries:

```
rdr pass on lo0 inet proto tcp from any to any port 22 -> 127.0.0.1 port 2222
```

Loaded into `/etc/pf.conf`'s anchor list with `anchor "tainer"` + `load anchor "tainer" from "/etc/pf.anchors/tainer"`. `pfctl -e` enables pf if not already. The user gets `ssh project@ssh.tainer.me` (no port). Removal mirrors in `tainer self-uninstall`.

## Conveniences

### Auto-port-publish

`tainer.yaml` v2 declares `ports:`:

```yaml
ports:
  - role: db
    container: 3306
  - role: mailpit
    container: 8025
```

At `tainer start`, for each entry:
1. If the container already exists (`tainer stop && tainer start` case) and has a `tainer.published.<role>` label, attempt to reuse that host port. Probe the host port with a TCP listen test; on success, bind that port. On conflict (some other process grabbed it), fall through to step 2.
2. Walk port numbers from 30000 to 39999. For each, attempt `net.Listen("tcp", "127.0.0.1:<n>")` — if it succeeds, immediately close, then bind via `HostConfig.PortBindings` with that port. Record the binding in `tainer.published.<role>=<n>` label.
3. Print to user during start: `mariadb on 127.0.0.1:30001 (db)`.

`tainer status` reads back labels for the per-pod summary.

### `.tainer.local.yaml` overlay

- Same schema as `tainer.yaml`
- Path: `<project-dir>/.tainer.local.yaml` (next to `tainer.yaml`)
- Loaded after `tainer.yaml`; deep-merge wins at every leaf
- Added to `.gitignore` automatically on `tainer init`
- Use cases:
  - `pod.size: large` on a beefier dev machine (team default `small` lives in `tainer.yaml`)
  - Custom env vars not committed
  - Alternative `runtime.php`/`runtime.node` versions per developer

Implementation: `manifest.Load()` reads both files (silently skipping the local one if absent), merges via reflection-driven recursive overwrite, returns the resolved manifest. Deterministic for testing.

## Install / sudo batching

All sudo-requiring operations execute exactly once at install time. The runtime never escalates privileges.

macOS `.pkg` postinstall script (runs as root):

1. Place `/opt/tainer/bin/{tainer, cyberstackd, vmnet-helper}` (root-owned)
2. Symlink `/usr/local/bin/tainer → /opt/tainer/bin/tainer`
3. Write `/etc/resolver/tainer.me`:
   ```
   nameserver 127.0.0.1
   port 7753
   ```
4. Write `/etc/pf.anchors/tainer`:
   ```
   rdr pass on lo0 inet proto tcp from any to any port 22 -> 127.0.0.1 port 2222
   ```
5. Patch `/etc/pf.conf` to load the tainer anchor at boot (idempotent: scan for marker line first):
   ```
   anchor "tainer"
   load anchor "tainer" from "/etc/pf.anchors/tainer"
   ```
6. `pfctl -e -f /etc/pf.conf` to enable pf and reload rules
7. (Optional, post-0.9) launchd plist to auto-start cyberstackd at user login

`tainer self-uninstall` (one sudo prompt) reverses every step, leaving the host clean.

For non-`.pkg` install paths (homebrew tap, manual `make install`), provide `sudo tainer post-install` that runs the same operations.

## Cyberstack-side dependencies

This milestone introduces **one** new requirement on cyberstackd, all the rest already exists in 0.4:

- **NEW:** Embedded DNS responder. Listens on UDP `127.0.0.1:7753`, answers `*.tainer.me → 127.0.0.1`. Configurable via `-dns-port` flag, default 7753. ~50 lines of Go using `github.com/miekg/dns`. Lifecycle-bound to the daemon.

The remaining 8 cyberstack capabilities tainer 0.9 leans on (all shipped in 0.4):
- Network create/connect/disconnect/remove/list with labels
- Container create with `HostConfig.Resources` (memory, NanoCPUs), labels, mounts, env, port bindings
- Container start/stop/remove/inspect/list with label filters
- Container exec with stdcopy demux
- Container logs
- Image pull (cold-pull P50 = 494ms post-0.4)
- Volume create
- Daemon-wide network mode flag (`-network-mode=vmnet-helper|external-gvproxy`)

## Testing strategy

### Unit

- Every new package (`pod`, `network/mode`, `dns/pf`) gets exhaustive table-driven tests
- `manifest` v1 → v2 migration: golden-file tests with sample manifests of each project type
- `pod.split` — parameterized over (project type × pod size), assert `Σcontainer.memory == pod.total` and CPU sum is correct
- `router.UpdateConfig` — given a fixture pod set, assert generated Caddyfile and sshpiper upstream files match goldens
- `network.Mode` round-trip — write/read/parse the persistence file
- `auto-port-publish` — fake net.Listen probes, assert the search-up loop terminates correctly under various conflict patterns

### Integration (vs live cyberstackd)

Smoke-style; skip if no daemon reachable (mirrors the existing `TestPingLiveDaemon` pattern in `pkg/tainer/engine`):

- For each project type: `init → start → exec → status → stop → start → destroy`
- `tainer network mode set compat` while 2+ pods are running; assert all come back healthy after the switch
- DB export → import round-trip for WordPress, PHP, Kompozi

### Parity (vs 0.2.x)

A separate test suite (post-0.9 hardening) that runs the same 9-project-type scenarios on both 0.2.x and 0.9 (in side-by-side machines or sequenced runs), asserts feature parity. Out of scope for this design but flagged so the implementation plan reserves a hook for it.

## Acceptance criteria for 0.9

- `tainer init wordpress mywp && tainer start mywp` succeeds on a clean install
- All 9 project types pass start/stop/exec/status/list end-to-end
- `tainer db export` and `tainer db import` round-trip for WordPress, PHP, Kompozi
- `tainer network mode set compat` with 3 running pods: all 3 survive the switch and serve their domains afterwards
- Embedded DNS responder answers `*.tainer.me → 127.0.0.1` on `127.0.0.1:7753`
- `/etc/resolver/tainer.me` and `/etc/pf.anchors/tainer` correctly installed by the postinstall script; `tainer self-uninstall` reverses cleanly
- Cold start of first project ≤ 0.2.x baseline (target: faster, since cyberstack 0.4 cold-pull is 494ms vs whatever podman+macOS gave us)
- Idle resident memory: cyberstackd + router caddy + sshpiper < 200 MB

## Roadmap notes

- **0.9 → 1.0 path:** smart pods (aggregate cgroup limits) requires a parent-cgroup-per-pod mechanism in cyberstackd's agent. Sized as one cyberstack milestone (0.5). Tainer 1.0 picks it up by adding `pod.size` interpretation: instead of computing per-container splits and applying them independently, the manifest's pod-size becomes the parent cgroup budget; per-container limits are then unset (containers compete inside the budget). Fully transparent to manifests written today — `pod.size: small` on 0.9 enforces statically, on 1.0 enforces aggregately.
- **Blenzi alignment:** the 5+1 pod size tiers (nano → xxl) become Blenzi plan tiers post-1.0. Tiers above xxl (3xl=32 GB, 4xl=64 GB) get added when commercial demand justifies them. The split tables freeze at 1.0 to make tier semantics stable for paying customers.
